# UI architecture

Svelte 5 + CodeMirror 6, organised by feature under `src/`. What the UI does is in `SPEC.md` §10; this file is how it is built.

## Rules

- `features` import `lib/*` and `state`; `lib/*` imports nothing from `features`, `state` or `app`.
- A feature imports another only through its `index.ts`. `app` composes features through snippets and props.
- Components get data from props or stores. Only `state/backend.ts` talks to the connection.
- Components use tokens (`var(--seen)`, `var(--h-row)`), never literal colours or sizes. The editor reads row heights from the tokens at construction.
- `eslint.config.js` enforces the import rules and the editor's no-Svelte rule (`pnpm lint`), plus import cycles.
- Events: `state/changeset.svelte.ts` subscribes to the backend's events (refetch on `snapshotSettled`, refetch and leave any range on `changesetOpened`, update one file on `reviewChanged` unless a range is shown, set `manifest.review` on `reviewStarted` and `manifest.base` on `baseChanged`); `queue`, `versions`, `threads` and the progress store subscribe to the ones they list. Views listen to the stores, not the connection.
- One component per file, named by what it is. No `utils`/`helpers`; put a function next to its user, or in `lib/` if shared.

## Reactivity

- Backend data lives in `state/` as immutable snapshots (`$state.raw`), one reactive cell per file (`SvelteMap<path, FileChange>`), never deep `$state`: proxies over thousands of files and hunks cost memory and every read. `changeset.manifest` is the manifest of the last refresh with the changeset completion kept current; `changeset.file(path)` is a file's current state.
- No full rebuilds. A `$derived` over a large collection is keyed or incremental: one `ReviewChanged` or `SetSeen` reply invalidates only that file's cell, and with it the tree row and tab that show it. The file tree's structure depends on `changeset.paths`, which keeps its identity while only review state changes, so it is built once per revision; a row reads its own file.
- The editor and virtualized views get explicit calls (`applyReview(path, review)`, `goToHunk`, `setMode`); they never subscribe to stores, and editor state is never mirrored into Svelte state.
- Nothing reactive per frame: no `$effect` or reactive state on what changes with a scroll position, a pointer move or a keystroke. Mounting editors while scrolling is imperative, and spends at most a few milliseconds per frame (the rest follows on the next frames).
- Small UI state is plain `$state`: tool windows, widths, theme, tabs, menus, toasts.

## Controls and selection

Controls take one of two classes from `global.css`, which applies the state tokens (`--hov`, `--press`, `--tog`, `--focus`): `.flat` (borderless: icon buttons, rows, menu items) and `.ctl` (bordered: chips, text buttons; `.ctl-group` joins several). Toggled is `aria-pressed="true"` or `.on`. A new control takes one of the classes and does not restyle its states; editor widgets use the same classes.

Chrome is not selectable (`user-select: none` on `body`); content meant to be copied opts in with `.selectable`.

## Commands and menus

Every action a key, a menu or a tooltip names is a command in one registry (`state/commands.ts`, built on `lib/commands.ts`): an id, a label, a default binding (data, so a Keymap page can override it), an "enabled when" over a `CommandContext`, and what it runs. App-wide commands are in `state/appCommands.ts`; the review screen's in `features/review/reviewCommands.ts`, registered by `ReviewController` (view commands) and `ReviewScreen` (files and tabs), which also provide the context facts they own (active tab, current hunk, focused editor).

- **Keys:** `App` installs the one capturing `keydown` listener, which calls `commands.dispatch`. Text input (AltGr, dead keys, IME) never matches; a command skips text fields unless it sets `inFields`; a command whose `run` answers `false` leaves its key to the page.
- **Menus:** a menu is a description of command ids (`MenuSpec`), resolved to items with labels, shortcuts and enabled state by `menuFor`, which also returns the context to run the choice in. `state/mainMenu.ts` describes the main menu (File, View, VCS with Fetch, Help; on macOS an app menu in front, and the host adds Edit so the webview gets copy, paste and undo); on macOS the host draws it natively (`state/mainMenu.svelte.ts` sends it to `set_menu`, a chosen item comes back as the `vet-menu` event and runs `commands.run(id)`), elsewhere the `TitleBar` draws it with `Menu`.
- **Accelerators:** a command whose `accelerator` is set (`Cmd+,` for Settings, `Cmd+Q` for Quit) is registered by the native menu bar, which handles the key itself; every other item shows the window's binding as text and the window's key handler runs it. The Keymap page (`features/settings/KeymapPage.svelte`, `lib/keymapEdit.ts`, `state/keymap.svelte.ts`) edits the bindings; the changes are kept in the browser storage and applied to the registry, so menus and tooltips follow.
- **Context menus** (file tree, file header, editors, tabs) are descriptions in `reviewCommands.ts`, opened through `state/contextMenu.svelte.ts`. In the Tauri host the host pops them up (`show_context_menu`) and the choice comes back as a promise; a menu that fails to show, and a plain browser, falls to `ContextMenu`, which `App` draws. The native menu shows a command's shortcut as the OS does: an accelerator on macOS (right-aligned, in the OS's glyphs), text after a tab on Windows, none elsewhere. The window's key handler still runs the key. An editor's menu acts on the editor that was clicked, and the focus returns to where it was before the choice runs.
- **Tooltips** of buttons that run a command take their shortcut from `commands.tooltip(id)`.

## Host

At launch the host opens a splash window (`splash.html` and `src/splash.ts`, a second Vite entry; `features/splash/`) and starts the backend on a thread, reporting each step to it (`state/host.ts`: `onStartupProgress`, `startupProgress`, `retryStartup`). The main window loads hidden meanwhile; `App` shows it once its backend connection is up, or failed with its own error, and the host then closes the splash. A failed start keeps the splash with Retry and Quit.

One window shows either the welcome screen or a project, and keeps a position and size for each (`src-tauri/src/geometry.rs`, saved as `window-geometry.json` in the app config dir; a saved place on a display that is gone falls back to the default). The host places the hidden window for its first mode before showing it; `session.svelte.ts` switches the mode (`setWindowMode`) before the content changes, so the window moves once.

The host passes the repository to open (command line or `VET_REPO`; in a plain browser `#repo=`). The folder dialog and the file picker are Tauri commands behind `state/host.ts`; the recent list is the backend's (`state/recent.svelte.ts`, each project with when it was last opened); the app version comes from the host (`appVersion`); paths stay backend-side strings (in the WSL split the host turns `\\wsl.localhost\<distro>\…` into the Linux path).

Personal access tokens are kept by the host in the operating system's keychain (`src-tauri/src/credentials.rs`; the hosts that have one are listed in `credential-hosts.json` of the app config dir, never a token). The backend holds tokens in memory only, so `state/accounts.svelte.ts` hands it every stored token when the connection is up and again when it asks (`credentialsNeeded`). `THIRD_PARTY_NOTICES.md` at the repository root is bundled as a resource of the application (`tauri.conf.json`).

## Screens

`App` shows one of two screens under the header: the queue (`features/queue/QueueScreen.svelte`) or the review (`ReviewScreen` with the tool rails). The project opens on the queue. A `Segmented` toggle in the `Header` switches; opening a file or a thread from the queue's panel switches to the review at that place. The review screen stays mounted while the queue shows: it is laid out but `visibility: hidden` and `inert`, so its editors keep their size and scroll positions, and nothing of it shows through the queue.

- **Queue:** `state/queue.svelte.ts` holds the backend's changeset rows (`ListChangesets`) and which one is on view, and reloads on `changesetOpened`, `reviewStarted` and `threadsChanged`. The table's tabs (All, Blocking, Local, Pull requests) are `PanelTabs` over `queueRows.ts`, which words each row's Source, Updated and progress cells; the panel under it shows the selected changeset's Details (`details.ts`), Files and Comments. Choosing a row puts that changeset on view (`changeset.openChangeset`); Enter or a double click also shows the review. The header's refresh button fetches the remotes and lists again.
- **Switchers:** the header's project switcher (`features/welcome/ProjectSwitcher.svelte`) lists the recent projects; the changeset switcher (`features/queue/ChangesetSwitcher.svelte`) is a `Popover` over the same rows with the queue's tabs as filters, listed afresh each time it opens, and a row that shows the queue. Each changeset keeps its open tabs, scroll positions and current hunk while another is on view (`ReviewController` parks them by `state/changesetKey.ts`'s key).
- **Header:** on the review it shows the changeset switcher, then the base picker (`BaseChip`), an arrow and the target: the version while a review is open, else the branch or commit; a dot marks the working tree as live. While a range of versions is shown, the range's chips take the place of the base and the progress, and a button leads back to the changeset.
- **Popovers:** the editors stack their layers up to `z-index: 1000`. The review's panes are an isolated stacking context, so the header's popovers (switchers, base picker) lie above them.

## Timeline

The timeline (`features/timeline/`) is a panel under the editors, opened from the left rail (`ReviewScreen`'s `bottom` snippet). `state/versions.svelte.ts` holds the review's versions as the backend lists them and reloads on `snapshotSettled`, `reviewStarted`, `reviewChanged` and `changesetOpened`. Its table lists the versions newest first with the files and lines each changed (`timelineRows.ts`); a click chooses what changed since the version before, a shift-click the span between two.

A range of versions is a mode of the review view, not a screen. `changeset.range` (`state/timelineRange.ts`: from, to, and whether its end follows the working tree) decides the `View` that every request about the files carries (`state/view.ts`: the changeset, or the interdiff of two versions); the manifest, the file contents and the review state are then those of the range, and views are rebuilt as for a new revision. A live end moves to the new latest version when a snapshot settles; only the working tree has one. The range reads marks and comments of its newer version and is read-only unless it ends at the latest version. Opening the timeline, and the "Changes Since My Last Review" command, choose the range from the version something was last marked in to the latest. The footer names the range as `v14 → v17`; `changeset.viewKey` tells views and threads which range they were read for.

## Views

Each tab's pane hands its scroll root to `ReviewController.attach`, which builds a `ChangesetView` in it (a read-only `TextView` for an unchanged file). `App` passes the changeset store down through `ReviewScreen`; the controller sees it only as a `ChangesetSource`. Views get file contents from an `editor/fileSource.ts` bound to their revision, never from the backend directly. Panes stay laid out when inactive (`visibility: hidden`), so scroll positions and editors survive switching. A new manifest revision rebuilds every view.

- Heights come from the manifest, not from CodeMirror, which estimates what is off screen. `editor/sectionLayout.ts` mirrors `collapseUnchanged` to compute a section's height, including change cards (fixed heights, nothing measured); `editor/sectionHeights.ts` keeps the column's positions, measures thread cards (one `ResizeObserver` per view, estimated until then) and keeps the scroll position when a section above the viewport resizes. Expanding a region grows its section by exactly the lines it hid; unmounting a section resets it to the estimate. `editor/windowing.ts` decides which sections get an editor and which load image previews.
- Wrapping is by file kind, with no toggle: prose (Markdown, reStructuredText, plain text; `editor/softWrap.ts`) wraps, code scrolls sideways. A wrapping section is laid out at one row per line until its text has arrived; `editor/wrapRows.ts` then works out each line's rows from the character width of the loaded font, the width of the code column (the view's width less the gutters, halved in side by side) and the tab size, and `sectionLayout` adds those rows to the section's height. A wrapping editor reports the height CodeMirror measured (`reportHeight`), which replaces the estimate; a new width re-estimates the sections without an editor.
- A long line scrolls its editor sideways, each editor and each pane of a side by side view by itself (`section.css`); the scroll bar is hidden, the view moves by gesture, key and caret. Hunk bars and change cards stay in view while the text scrolls, and thread cards size to the pane. `editor/longLines.ts` marks a changed line wider than the code column in the line number gutter, wrapped or not.
- Only the current section's header is `position: sticky` (class `pinned`): thousands of sticky headers would cost the browser more on every scroll than one. `editor/pinned.ts` picks the pinned file and hunk from the height model's positions for a scroll offset, and `editor/stickyHunk.ts` draws the pinned hunk bar under the header as one element that follows the scroll, since the real bar lives inside an editor that renders only what is near the viewport.
- Hover popups (`editor/hoverPopup.ts` for when, `hoverDom.ts` for where) are one fixed element in the body, above the symbol, because a side by side pane clips what it contains. A popup belongs to the symbol under the pointer: it stays while the pointer is on the symbol or the popup, and only another symbol replaces it.
- Benchmark-only access to a view goes through `editor/viewProbe.ts`, handed out only to the dev tools; production code paths carry no dev API.
- The UI computes no diff of a changeset file: `FileContents` carries the changed ranges (`changes`, down to the words that differ), and `editor/backendDiff.ts` hands them to `@codemirror/merge` as its `diffConfig.override`. Every editor is read-only: Vet never writes the tree, so the text always matches what the backend's positions refer to.
- The UI parses no code: syntax highlights come with `FileContents`, `FileText` and hover code blocks, and `editor/highlights.ts` turns them into classes.
- Layout reads happen in CodeMirror's measure phase (`requestMeasure`), never on the mount path. A plugin asks for a measure only on changes that can alter what it reads (document, viewport, its own effects), never on a height-only update: those come from the measure phase itself, and asking from one restarts CodeMirror's measure loop. `gutterWidth.ts` publishes the gutters' width once per editor as `--vet-gutters`.
- Lists (the file tree's scopes) render through `lib/ui/VirtualRows`: fixed row height from `--h-row`, only the visible rows plus a margin in the DOM. Directory listings carry the revision they belong to; a reply of another revision is dropped.
- The Changes tab is labelled "All changes" with the number of changed files; a file's tab carries the file's name.

## Chrome

- **Icons:** `lib/ui/icons.ts` is the one table of UI icons, 24×24 paths drawn as strokes or, for the solid ones, filled; `Icon.svelte` draws them and `iconSvg` builds the same markup for CodeMirror widgets. The review toggle is Lucide's file-diff, and the hosting platforms' marks (GitHub, Azure DevOps) are simple-icons'. File-type icons are separate: `lib/fileIcons.ts` picks one by name alone (a map read per row) and `lib/ui/fileIconUrls.ts` holds the pictures.
- **Speed search:** typing into a focused list, tree or menu narrows it. `lib/speedSearch.ts` matches a query against a name (word starts and runs after them rank first) and gives the ranges to highlight; `lib/ui/speedSearch.svelte.ts` is the state one list keeps and `SpeedSearchField` shows it. While a search is active command keys leave typing to it (`SEARCHING`).
- **Background progress:** the backend's tasks (scanning, diffing, restoring, servers starting, indexing, the symbol analysis) reach `state/progress.svelte.ts`, which keeps the running ones in a `TaskBoard` and shows a task only once it has run for a moment, so a rescan after an edit does not flash. `StatusFooter` takes them as a snippet, drawn by `TaskProgress`: the newest task and how many others run (`state/taskHeadline.ts`). The footer names a language server only while a file's tab is active, never on the Changes tab.
- **Settings:** `SettingsDialog` lists its pages on the left. Appearance is the theme; Keymap edits bindings; Review edits the repository's review filter; Language servers lists the servers the backend resolved and installs missing ones (`state/servers.svelte.ts`); Accounts (`state/accounts.svelte.ts`) is a table of hosts with the platform's mark, the account and how its credential was found (a CLI's login or a personal access token), details under it, and a sheet to add a token, which the platform checks before it is kept.

## Threads

`state/threads.svelte.ts` holds the backend's threads, resolved at one revision, and reloads on `threadsChanged` and `snapshotSettled`. `ReviewController` hands them to every view whose revision matches. In a view, `editor/threadLayer.ts` owns them: range threads are block widgets (`threadWidgets.ts`) below the target line the backend sends with each thread; file and changeset threads are blocks outside the editor.

## Semantics

Hover, go to definition and diagnostics reach every editor through `editor/semantic.ts`, which asks its owner through `SemanticHooks` (Cmd/Ctrl+B is the `review.goToDefinition` command, reading the focused editor that `semantic.ts` tags); `bindRevision` fixes the revision of a view's requests, since the backend rejects a stale one. `state/semantic.svelte.ts` drops a stale answer.

- Positions are 0-based lines and UTF-16 columns of the side asked about. In a unified view the deleted lines are widgets outside the document, so `editor/deletedLines.ts` maps the pointer to a base position from the DOM.
- Hover text comes from an external process and is untrusted: `editor/hoverMarkdown.ts` renders it with raw HTML escaped, no images and no link targets.
- Unavailable (SPEC I6) is never shown as nothing: `state/semanticSummary.ts` turns it into the footer's language-server text.

## Where things go

- New screen: `features/<name>/` with an `index.ts`; mount it from `app/App.svelte`.
- New backend request: a method in `state/backend.ts`, then a store field if the UI displays it. A request that can fail in a way the viewer should hear about goes through the store, which sets `session.notice` (shown as a `Toast` in `App`).
- Data the protocol does not carry yet is an optional prop whose absence renders a neutral empty state; fixtures for it live in `dev/` and never reach a production code path.
- Colour or size: `lib/theme/tokens.css` (and a `dev` check in both themes).
- New sidebar tool: an entry in `chrome/ToolRail`, its content as a snippet from `App`.
- New settings page: a component in `features/settings/` and an entry in `SettingsDialog`'s page list.
- New kind of changeset in the queue: the backend's `ChangesetKey` variant, and the tab it is listed under in `queueRows.categoryOf`.
- New tab kind: an id in `Tabs.svelte.ts`, a pane in `ReviewScreen`, and a case in `ReviewController.build`.
- New action with a key or a menu entry: a command registered with `commands`, named by id in the menu descriptions that offer it.
