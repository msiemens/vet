## Rules

- `features` import `lib/*` and `state`; `lib/*` imports nothing from `features`, `state` or `app`.
- A feature imports another only through its `index.ts`. `app` composes features through snippets and props.
- Components get data from props or stores. Only `state/backend.ts` talks to the connection.
- Components use tokens (`var(--seen)`, `var(--h-row)`), never literal colours or sizes. The editor reads row heights from the tokens at construction.
- `eslint.config.js` enforces the import rules and the editor's no-Svelte rule (`pnpm lint`), plus import cycles.
- Events: the stores subscribe to the backend's events as [Events](#events) lists. Views listen to the stores, not the connection.
- One component per file, named by what it is. No `utils`/`helpers`; put a function next to its user, or in `lib/` if shared.

## Events

Every event a request causes reaches every subscriber, the window that asked included: only the store that asked reads the answer, and every other store of that window learns of the change from the event alone. So a store follows the events of what it shows and never relies on another store's request; a reload that the requester's own answer makes redundant is harmless. `vet-backend/src/contract.rs` says which request sends which event, and its test checks it. The events of the backend itself (`credentialsNeeded`, `accountsChanged`, `recentProjectsChanged`) reach the windows that asked for `accounts()` or `recentProjects()`, through `onCredentialsNeeded`, `onAccountsChanged` and `onRecentProjectsChanged`; `onEvent` hands over those of the open project. Events sent while the connection was down are lost: [Connection](#connection) says how the stores catch up.

## Reactivity

- Backend data lives in `state/` as immutable snapshots (`$state.raw`), one reactive cell per file (`SvelteMap<path, FileChange>`), never deep `$state`: proxies over thousands of files and hunks cost memory and every read. `changeset.manifest` is the manifest of the last refresh with the changeset completion kept current; `changeset.file(path)` is a file's current state.
- No full rebuilds. A `$derived` over a large collection is keyed or incremental: one `ReviewChanged` or `SetSeen` reply invalidates only that file's cell, and with it the tree row and tab that show it. The file tree's structure depends on `changeset.paths`, which keeps its identity while only review state changes, so it is built once per revision; a row reads its own file.
- The editor and virtualized views get explicit calls (`applyReview(path, review)`, `goToHunk`, `setMode`); they never subscribe to stores, and editor state is never mirrored into Svelte state.
- Nothing reactive per frame: no `$effect` or reactive state on what changes with a scroll position, a pointer move or a keystroke. Mounting editors while scrolling is imperative, and spends at most a few milliseconds per frame (the rest follows on the next frames).
- Small UI state is plain `$state`: tool windows, widths, theme, tabs, menus, toasts.

## Controls and selection

Controls take one of two classes from `global.css`, which applies the state tokens (`--hov`, `--press`, `--tog`, `--focus`): `.flat` (borderless: icon buttons, rows, menu items) and `.ctl` (bordered: chips, text buttons; `.ctl-group` joins several). Toggled is `aria-pressed="true"` or `.on`. A new control takes one of the classes and does not restyle its states; editor widgets use the same classes.

Chrome is not selectable (`user-select: none` on `body`); content meant to be copied opts in with `.selectable`.

Lists share one rule (`lib/ui/listNav.ts`, `lib/listKeys.ts`): a click runs the row's single action, a double click only its open action, ↑/↓ move a highlight, Space is the single action and Enter the open one; the list container is the tab stop and carries `data-list`, inside which commands marked `yieldsToLists` (Toggle Seen on Space) do not run. `ClickGate` (`lib/ui/doubleClick.ts`) holds a click's single action for the system's double-click time, which the host reports (`double_click_ms`; read at start and on focus, 500 ms in a plain browser), so a double click never runs it first. The file tree, the Symbol list, the queue table and the queue's Files and Comments lists use it.

## Commands and menus

Every action a key, a menu or a tooltip names is a command in one registry (`state/commands.ts`, built on `lib/commands.ts`): an id, a label, a default binding (data, so a Keymap page can override it), an "enabled when" over a `CommandContext`, and what it runs. App-wide commands are in `state/appCommands.ts`; the review screen's in `features/review/reviewCommands.ts`, registered by `ReviewController` (view commands) and `ReviewScreen` (files and tabs), which also provide the context facts they own (active tab, current hunk, focused editor).

- **Keys:** `App` installs the one capturing `keydown` listener, which calls `commands.dispatch`. Text input (AltGr, dead keys, IME) never matches; a command skips text fields unless it sets `inFields`; a command whose `run` answers `false` leaves its key to the page.
- **Menus:** a menu is a description of command ids (`MenuSpec`), resolved to items with labels, shortcuts and enabled state by `menuFor`, which also returns the context to run the choice in. `state/mainMenu.ts` describes the main menu (File, View, VCS with Fetch, Help; on macOS an app menu in front, and the host adds Edit so the webview gets copy, paste and undo); on macOS the host draws it natively (`state/mainMenu.svelte.ts` sends it to `set_menu`, a chosen item comes back as the `vet-menu` event and runs `commands.run(id)`), elsewhere the `TitleBar` draws it with `Menu`.
- **Accelerators:** a command whose `accelerator` is set (`Cmd+,` for Settings, `Cmd+Q` for Quit) is registered by the native menu bar, which handles the key itself; every other item shows the window's binding as text and the window's key handler runs it. The Keymap page (`features/settings/KeymapPage.svelte`, `lib/keymapEdit.ts`, `state/keymap.svelte.ts`) edits the bindings; the changes are kept in the browser storage and applied to the registry, so menus and tooltips follow.
- **Context menus** (file tree, file header, editors, tabs) are descriptions in `reviewCommands.ts`, opened through `state/contextMenu.svelte.ts`. In the Tauri host the host pops them up (`show_context_menu`) and the choice comes back as a promise; a menu that fails to show, and a plain browser, falls to `ContextMenu`, which `App` draws. The native menu shows a command's shortcut as the OS does: an accelerator on macOS (right-aligned, in the OS's glyphs), text after a tab on Windows, none elsewhere. The window's key handler still runs the key. An editor's menu acts on the editor that was clicked, and the focus returns to where it was before the choice runs.
- **Tooltips** of buttons that run a command take their shortcut from `commands.tooltip(id)`.
- **Tool windows:** the tools are listed once, in `TOOL_WINDOWS` (`state/appCommands.ts`): Changes, All files, Commits and Comments on the left rail, Symbol on the right, Timeline at the bottom. Each has the command `view.tool.<id>` (Alt+1 to 6), which `App` runs through `toggleTool`: the selected tool's key hides or shows its sidebar, any other selects its tool and shows it; the rail's icons run the same commands (`ToolRail`, which also draws a tool's count and, at the bottom of the left rail, the timeline's icon). A tool that cannot be picked shows its command's disabled reason (Commits needs a changeset of several commits; its command is disabled then). Commits and the by-commit lens go together (`chrome/commitsTool.ts`): selecting the tool asks for the lens, leaving it asks for All changes, and a lens set elsewhere selects or leaves the tool.

## Host

At launch the host opens a splash window (`splash.html` and `src/splash.ts`, a second Vite entry; `features/splash/`) and starts the backend on a thread, reporting each step to it (`state/host.ts`: `onStartupProgress`, `startupProgress`, `retryStartup`). The main window loads hidden meanwhile; `App` shows it once its backend connection is up, or failed with its own error, and the host then closes the splash. A failed start keeps the splash with Retry and Quit.

One window shows either the welcome screen or a project, and keeps a position and size for each (`src-tauri/src/geometry.rs`, saved as `window-geometry.json` in the app config dir; a saved place on a display that is gone falls back to the default). The host places the hidden window for its first mode before showing it; `session.svelte.ts` switches the mode (`setWindowMode`) before the content changes, so the window moves once.

The host passes the repository to open (command line or `VET_REPO`; in a plain browser `#repo=`). The folder dialog and the file picker are Tauri commands behind `state/host.ts`; the recent list is the backend's (`state/recent.svelte.ts`, each project with when it was last opened); the app version comes from the host (`appVersion`); paths stay backend-side strings (in the WSL split the host turns `\\wsl.localhost\<distro>\…` into the Linux path).

`open_url` (`src-tauri/src/browser.rs`, behind `state/host.ts`'s `openUrl`) shows a web address in the user's browser; it opens only `http(s)` addresses, since they come from the backend (a platform's page for a check).

Personal access tokens are kept by the host in the operating system's keychain (`src-tauri/src/credentials.rs`; the hosts that have one are listed in `credential-hosts.json` of the app config dir, never a token). The backend holds tokens in memory only, so `state/accounts.svelte.ts` hands it every stored token when the connection is up and again when it asks (`credentialsNeeded`). `THIRD_PARTY_NOTICES.md` at the repository root is bundled as a resource of the application (`tauri.conf.json`).

## Browser development

`pnpm dev` serves the UI at `http://localhost:1420` and starts no backend: the page talks to a real `vet-backend`, the same one the host spawns. Run `cargo run -p vet-backend` (its first stdout line is `{"port":…,"token":"…"}`) and open `http://localhost:1420/#port=<port>&token=<token>&repo=<path>`; without `repo` the welcome screen asks for one. Outside Tauri `state/backend.ts`'s dialer reads the address from the URL hash and throws when `port` or `token` is missing. A plain browser is for development only: the host's commands (folder dialogs, keychain, native menus) fall back to browser behaviour or are off (`state/host.ts`), and the dev tools work there as in the host. The data directory is the backend's own; set `HOME` to a scratch directory to keep a trial run away from the real one.

## Connection

The backend is a process the host supervises (`src-tauri/src/backend.rs`). A thread per started backend watches its output, which ends when it exits; the host then starts another, on a new port with a new token, unless that would be its fourth exit within a minute, after which it stays down until the viewer restarts it. `backend_connection` answers with the address of the backend running now (an error while one is starting or after it was given up on) and `restart_backend` ends the backend and starts another, also after it was given up on. The lint that keeps blocking work and processes behind the backend's budgets (`crates/clippy.toml`, see `ARCHITECTURE.md`) does not cover this crate, which spawns threads and the backend process itself.

`state/connection.ts` connects again when the socket drops, with no help from its users:

- The requests that were on the dropped socket fail, since the backend may have carried them out, and are not sent again. A request made while connecting again waits up to 10 s for the connection.
- It asks the dialer for the backend's address before each attempt (a restarted backend listens elsewhere) and tries after 0.2, 0.5, 1, 2 and then every 5 s. The link is `reconnecting`, and `stalled` after 30 s of that; `session.link` carries it, and only a stalled link is shown: `ConnectionNotice` says the backend does not answer and, in the host, offers Restart (`session.restartBackend` asks the host, then tries to connect at once with `retryConnection`).
- Once connected again, the new backend connection knows nothing of the window. `session.svelte.ts` opens the open repository on it again, which subscribes to its events (a repository that cannot be opened ends in the welcome screen), reloads the recent list and calls the `session.onResync` listeners. Every store that holds what the backend sent reads it again there, as it would for the events it may have missed (changeset, queue, versions, threads, checks, platform, tasks, language servers); `state/accounts.svelte.ts` hands the new backend its tokens again.

## Screens

`App` shows one of two screens under the header: the queue (`features/queue/QueueScreen.svelte`) or the review (`ReviewScreen` with the tool rails). The project opens on the queue. A `Segmented` toggle in the `Header` switches; opening a file or a thread from the queue's panel switches to the review at that place. The review screen stays mounted while the queue shows: it is laid out but `visibility: hidden` and `inert`, so its editors keep their size and scroll positions, and nothing of it shows through the queue.

- **Queue:** `state/queue.svelte.ts` holds the backend's changeset rows (`ListChangesets`) and which one is on view, and reloads on the events [Events](#events) lists for it. The table's tabs (All, Blocking, Local, Pull requests) are `PanelTabs` over `queueRows.ts`, which words each row's Source, Updated and progress cells; the panel under it shows the selected changeset's Details (`details.ts`), Files and Comments. A click or Space selects a row for the panel; Enter or a double click opens it (`changeset.open:<id>`). The header's refresh button fetches the remotes and lists again.
- **Switchers:** the header's project switcher (`features/welcome/ProjectSwitcher.svelte`) lists the recent projects; the changeset switcher (`features/queue/ChangesetSwitcher.svelte`) is a `Popover` over the same rows with the queue's tabs as filters, listed afresh each time it opens, and a row that shows the queue. Each changeset keeps its open tabs, scroll positions and current hunk while another is on view (`ReviewController` parks them by `state/changesetKey.ts`'s key).
- **Header:** on the review it shows the changeset switcher, then the base picker (`BaseChip`), an arrow and the target: the version while a review is open, else the branch or commit; a dot marks the working tree as live. While a range of versions is shown, the range's chips take the place of the base and the progress, and a button leads back to the changeset. The toolbar ends with Finish review (while a review is open) and, on a pull request, the head commit's checks and the outgoing-comments button ([Threads](#threads)). `Target.head` is the tip's full id: the checks are asked for by it, and the UI shortens it only to show it.
- **Popovers:** the editors stack their layers up to `z-index: 1000`. The review's panes are an isolated stacking context, so the header's popovers (switchers, base picker) lie above them.

## Timeline

The timeline (`features/timeline/`) is a panel under the editors, opened from the left rail (`ReviewScreen`'s `bottom` snippet). `state/versions.svelte.ts` holds the review's versions as the backend lists them and reloads on `snapshotSettled`, `reviewStarted`, `reviewChanged` (of any window, this one included) and `changesetOpened`. Its table lists the versions newest first with the files and lines each changed (`timelineRows.ts`); a click chooses what changed since the version before, a shift-click the span between two.

A range of versions is a mode of the review view, not a screen. `changeset.range` (`state/timelineRange.ts`: from, to, and whether its end follows the working tree) decides the `View` that every request about the files carries (`state/view.ts`: the changeset, or the interdiff of two versions); the manifest, the file contents and the review state are then those of the range, and views are rebuilt as for a new revision. A live end moves to the new latest version when a snapshot settles; only the working tree has one. The range reads marks and comments of its newer version and is read-only unless it ends at the latest version. Opening the timeline, and the "Changes Since My Last Review" command, choose the range from the version something was last marked in to the latest. The footer names the range as `v14 → v17`; `changeset.viewKey` tells views and threads which range they were read for.

## By-commit lens

A branch or pull request is reviewed All changes or By commit; the backend's `manifest.lens` says which (SPEC §6, `SetLens`). By commit, `state/changeset.svelte.ts` loads `commits` (the `Commits` request: each commit with its own delta and progress, merges marked) and shows one of them: `commitIndex` makes `view` a `View::Commit`, so every request about files names that commit, and `shownCommit` follows with the manifest. `state/commitLens.ts` decides which commit shows (none for a changeset of one commit or none, which has nothing to go through) and the neighbour of a step. A range of versions takes the place of a commit and the lens brings it back; a mark made in a commit is announced as the changeset's file, so the store applies its totals without replacing the commit's file.

The Files window has the panel tabs Changes | Commits (`features/review/CommitList.svelte`, rows worded by `commitRows.ts`); the tree under the list shows only the selected commit's files. The Changes tab's header is `CommitHeader` (author, time, hash, checks, message). `[` and `]` step through the commits (`reviewCommands.ts`), next-hunk on a commit's last hunk continues into the next, and the footer shows `n / m`. A clean merge is muted, counts as complete and shows an empty editor.

## Base-changed lines

Hunks seen against an older base (`oldBaseLines` per hunk and in every completion) draw as diagonal amber stripes in the review strip and as an amber segment in the meters, after the blue one; the percentage counts only the blue. The hunk bar has a toggle that opens the hunk's base diff under it (`editor/baseDiffBlock.ts`, a widget of fixed height; the lines come from `BaseDiff` when it opens, and a side-by-side hunk's base side has no toggle) and, in place of the check, Re-confirm; the file header re-confirms a file's hunks (`ReconfirmFile`). "Base changed" in the queue's Details links to the Review screen with the Changes tab filtered: `changeset.baseChanged` holds the shown files, `shownFiles` is what the tab lists, `ReviewController` rebuilds its views for them, and the toolbar offers Re-confirm all and a way back. A range of versions leaves the filter.

## Views

Each tab's pane hands its scroll root to `ReviewController.attach`, which builds a `ChangesetView` in it (a read-only `TextView` for an unchanged file). `App` passes the changeset store down through `ReviewScreen`; the controller sees it only as a `ChangesetSource`. Views get file contents from an `editor/fileSource.ts` bound to their revision, never from the backend directly. Panes stay laid out when inactive (`visibility: hidden`), so scroll positions and editors survive switching. A new manifest revision rebuilds every view.

- Heights come from the manifest, not from CodeMirror, which estimates what is off screen. `editor/sectionLayout.ts` mirrors `collapseUnchanged` to compute a section's height, including change cards (fixed heights, nothing measured); `editor/sectionHeights.ts` keeps the column's positions, measures thread slots (`.vet-thread`, the padding around a card; one `ResizeObserver` per view, estimated until then) and keeps the scroll position when a section above the viewport resizes. Expanding a region grows its section by exactly the lines it hid; unmounting a section resets it to the estimate. `editor/windowing.ts` decides which sections get an editor and which load image previews.
- Wrapping is the viewer's setting (General: Prose, All files or Never; `lib/softWrap.ts`, kept in the browser storage and handed by `App` to the controller, which builds the views anew). By default only prose (Markdown, reStructuredText, plain text; `editor/softWrap.ts` tells which files are) wraps, code scrolls sideways. A wrapping section is laid out at one row per line until its text has arrived; `editor/wrapRows.ts` then works out each line's rows from the character width of the loaded font, the width of the code column (the view's width less the gutters, halved in side by side) and the tab size, and `sectionLayout` adds those rows to the section's height. A wrapping editor reports the height CodeMirror measured (`reportHeight`), which replaces the estimate; a new width re-estimates the sections without an editor.
- A long line scrolls its editor sideways, each editor and each pane of a side by side view by itself (`section.css`); the horizontal scroll bar is hidden, the view moves by gesture, key and caret. The vertical bar of a view is Vet's own ([Chrome](#chrome)): the diff views and a changed file's text give it a mark per hunk, coloured by the hunk's review state (`editor/scrollMarks.ts`), so the whole changeset or file reads at a glance. Hunk bars and change cards stay in view while the text scrolls, and thread cards size to the pane. `editor/longLines.ts` marks a changed line wider than the code column in the line number gutter, wrapped or not.
- Only the current section's header is `position: sticky` (class `pinned`): thousands of sticky headers would cost the browser more on every scroll than one. `editor/pinned.ts` picks the pinned file and hunk from the height model's positions for a scroll offset, and `editor/stickyHunk.ts` draws the pinned hunk bar under the header as one element that follows the scroll, since the real bar lives inside an editor that renders only what is near the viewport.
- Hover popups (`editor/hoverPopup.ts` for when, `hoverDom.ts` for where) are one fixed element in the body, above the symbol, because a side by side pane clips what it contains. A popup belongs to the symbol under the pointer: it stays while the pointer is on the symbol or the popup, and only another symbol replaces it.
- The UI computes no diff of a changeset file: `FileContents` carries the changed ranges (`changes`, down to the words that differ), and `editor/backendDiff.ts` hands them to `@codemirror/merge` as its `diffConfig.override`. Every editor is read-only: Vet never writes the tree, so the text always matches what the backend's positions refer to.
- The UI parses no code: syntax highlights come with `FileContents`, `FileText` and hover code blocks, and `lib/highlights.ts` decodes them for `editor/highlightExtension.ts`, which turns them into classes.
- Layout reads happen in CodeMirror's measure phase (`requestMeasure`), never on the mount path. A plugin asks for a measure only on changes that can alter what it reads (document, viewport, its own effects), never on a height-only update: those come from the measure phase itself, and asking from one restarts CodeMirror's measure loop. `gutterWidth.ts` publishes the gutters' width once per editor as `--vet-gutters`.
- Lists (the file tree's scopes) render through `lib/ui/VirtualRows`: fixed row height from `--h-row`, only the visible rows plus a margin in the DOM. Directory listings carry the revision they belong to; a reply of another revision is dropped.
- The Changes tab is labelled "All changes" with the number of changed files, or, by commit, the commit's short hash and the number of its files; a file's tab carries the file's name.
- **File tabs** are one per file (`file:<path>`), with the view mode as the tab's state (`Tabs.svelte.ts` keeps a mode per tab; the pure rules — ids, the modes a tab offers, settling a mode, which tabs go stale — are in `tabModel.ts`). A changed file's tab has a diff pane (Unified or Split) and a text pane, built the first time File mode is chosen; each keeps its own caret and scroll, and the caret line carries across a switch. An unchanged file's tab has File mode only. The mode commands (Unified, Side-by-Side, File) change the active tab's mode and never open or close a tab; Jump to Source switches the file's tab to File mode at the line.
- **The text pane** (`editor/TextView.ts`) shows the target's text read-only. For a changed file this is its **File view**: the changes are drawn in the text, so a hunk can be marked seen in context. `editor/fileLayout.ts` works out, purely, which target lines a hunk added or changed, where lines were removed, which words differ on a modified line and how strongly the hunk's review state paints (what is left to review in full, what was seen faint); `editor/fileChanges.ts` keeps that with the review states the controller hands in (`applyReview`) and draws it: line and word tints, the review strip in the gutter, a wedge where lines were removed whose peek shows them from the base text, and the hunk the caret is in tinted blue over all that. `editor/hunkToolbar.ts` is the toolbar over the current hunk (mark seen, Comment; it fades and lets clicks through while it would cover code) and `editor/fileCard.ts` the card of a changed line (the old line with the replaced words marked, the hunk's review state). Next and previous hunk, Space and re-confirm work there as in the diff. The control above the editors (`ViewControls`) runs the mode commands; a double click in the diff switches to the File view at that line (`editor/openAtLine.ts`), as does opening a file from the tree; threads show in the File view below their target line (`editor/textThreads.ts`, sharing the card, widget and `threadActions` code with the diff views; base-side threads at their mapped target line), and a comment from the File view is composed there.
- **Where a comment goes** is decided in one place, `editor/commentAnchor.ts` (pure; the views hand in the selection of the editor the reviewer was last in): the command and the editor's menu comment on the selection, else on the caret's line; a hunk's Comment button on the whole hunk, or on the selection when it overlaps that hunk's lines on its side; in the File view the current hunk stands in for the removed lines of a removal, which have no line of their own. The result is a `CommentAt`, which the backend turns into the thread's target (`CommentTarget`).
- **Log tabs** (`editor/LogView.ts`, tab id `log:<run>`) show a CI job log read-only with line numbers, scrolled to the line where the job failed and marking it. The checks popover (`features/checks/ChecksButton.svelte`) opens one for a failed run that has a log; its names are kept in `Tabs.logs`.

## Chrome

- **Icons:** `lib/ui/icons.ts` is the one table of UI icons, 24×24 paths drawn as strokes or, for the solid ones, filled; `Icon.svelte` draws them and `iconSvg` builds the same markup for CodeMirror widgets. The review toggle is Lucide's file-diff, and the hosting platforms' marks (GitHub, Azure DevOps) are simple-icons'. File-type icons are separate: `lib/fileIcons.ts` picks one by name alone (a map read per row) and `lib/ui/fileIconUrls.ts` holds the pictures.
- **Speed search:** typing into a focused list, tree or menu narrows it. `lib/speedSearch.ts` matches a query against a name (word starts and runs after them rank first) and gives the ranges to highlight; `lib/ui/speedSearch.svelte.ts` is the state one list keeps and `SpeedSearchField` shows it. While a search is active command keys leave typing to it (`SEARCHING`).
- **Background progress:** the backend's tasks (scanning, diffing, restoring, servers starting, indexing, the symbol analysis) reach `state/progress.svelte.ts`, which keeps the running ones in a `TaskBoard` and shows a task only once it has run for a moment, so a rescan after an edit does not flash. `StatusFooter` takes them as a snippet, drawn by `TaskProgress`: the newest task and how many others run (`state/taskHeadline.ts`). The footer names a language server only while a file's tab is active, never on the Changes tab: `state/serverList.svelte.ts` keeps the open repository's servers (reloaded on `serversChanged`; hover popups name the server from it too), `state/serverStatus.ts` words the focused file's server with its state, and clicking the item opens Settings > Language servers. The platform item (`features/platform/PlatformFooter.svelte`) shows how the platform of the pull request on view is doing and turns orange when it cannot be synced with; clicking it opens Settings > Accounts (the `app.accounts` command, the one way in to sign-in). The bell at the footer's right lists the notifications the backend sent (`platform.notified`), which also show as cards in the corner; one that needs no answer leaves after a few seconds.
- **Dialogs:** `lib/ui/Dialog.svelte` is resizable when given a `resizable` key (Settings): from its sides and bottom corners, never beyond the window, and the size is kept in the browser storage under that key.
- **Scroll bars:** `lib/ui/scrollbar.ts` draws Vet's own vertical bar, a gutter beside the scroller that always shows and takes its own width, with a translucent thumb, and hides the platform's (`.vet-scroller`). It follows the content by observing it; `ChangesetView`, which knows its heights, turns that off and calls `refresh`. Marks can be drawn under the thumb: `Scrollbar` takes a `MarkLayout` (px in the content) and scales it to the track, so a one-line hunk of a long changeset stays visible. `lib/ui/ScrollArea.svelte` is a scroller with a bar, for panels and lists; a view that owns its scroller creates the `Scrollbar` itself.
- **Tables:** `lib/ui/Table.svelte` is a header over rows its owner draws, each row laid out on the header's grid. `columns.ts` holds the `Column` description (default width and minimum, one flexible column, fixed ones, right alignment, a `sortBy` that makes the column sortable) and the arithmetic of widths. The viewer resizes a column by dragging its divider or with the arrow keys on it and resets it with a double click; a click on a sortable header cycles its first direction, the other and the owner's own order (`sorting.ts`; the owner orders its rows with `sortRows`, rows without a value last either way). The widths and the sort are kept in the browser storage under the table's `name` (`vet.table.<name>`). The queue, the timeline and the Language servers and Accounts pages are tables.
- **Settings:** `SettingsDialog` lists its pages on the left. General holds the soft wrap setting ([Views](#views)) and how many days a finished review is kept, which is the backend's own setting (`state/backendSettings.svelte.ts`, read and changed without an open repository); Appearance is the theme; Keymap edits bindings; Review edits the repository's review filter; Language servers lists the servers the backend resolved and installs missing ones (`state/servers.svelte.ts`) and holds the semantic cache's budget and its Clear action; Accounts (`state/accounts.svelte.ts`) is a table of hosts with the platform's mark, the account and how its credential was found (a CLI's login or a personal access token) and details under it. `Sheet.svelte` is the form a page opens over the dialog (Accounts: add or replace a token, which the platform checks before it is kept; Language servers: a custom server path): a modal `dialog` of its own, so Escape and Tab belong to the sheet and not to the dialog beneath, closed by Escape unless it is busy.

## Threads

`state/threads.svelte.ts` holds the backend's threads, resolved at one revision, and reloads on `threadsChanged`, `snapshotSettled` and `changesetOpened`. `ReviewController` hands them to every view whose revision matches. In a view, `editor/threadLayer.ts` owns them: range threads are block widgets (`threadWidgets.ts`) below the target line the backend sends with each thread; file threads are blocks outside the editor. The changeset's own threads are not about code and are in no diff view, only in the Comments tool window. A pull request's threads carry what the backend synced: author avatars, resolved-by, drafts shown on a shaded background, and an edit made in two places (`message.conflict`), which the card shows as the two texts with the differing words marked (`editor/wordDiff.ts`) and a Keep button under each. The viewer edits and removes only their own comments; everything is the backend's call and the card renders the reply.

`features/comments/CommentsPanel.svelte` lists the threads on files and lines grouped as Conflicts, Open and Resolved (`groups.ts`). For a pull request it starts with `PullRequestBlock` (`state/platform.svelte.ts` holds the `PullRequestInfo`, reloaded on `platformStatus`, `threadsChanged` and `changesetOpened`) and `SubmitReview`, and has the tabs Review and Conversation (`PanelTabs`; the chosen tab is `platform.commentsTab`, so opening a changeset-level thread elsewhere can pick it). A changeset that is no pull request has the list alone. `conversation.ts` says what each tab lists. Review is the threads on files and lines. Conversation is what is said about the pull request as a whole: where `traits.conversationFeed` the platform's feed (`ConversationList`: comments and reviews, with the viewer's own editable, and the viewer's comments that wait for posting among them), else the changeset's own threads as cards (`ThreadCards`, built by `ReviewController.threadCard`, the cards the editors use). Without a pull request those cards come above the Review list. A comment on the changeset as a whole is written in this tool window.

Posting has one code path for its two places. `posting.ts`'s `sendComments` follows the traits: `batchedReview` submits the outgoing comments as one review with the verdict and summary of the form; otherwise it posts them one by one, and with `verdictSeparate` a vote control (`PostingControls.svelte`) sits beside, which stages the vote (`StageVote`) for the post to send after the comments. `SubmitReview.svelte` is the tool window's control (Submit review opens the form; Post posts at once). `OutgoingButton.svelte` is the header's, on a pull request: it counts the viewer's comments that the platform does not have yet, and the staged vote (`outgoing.ts`; red with the number of failed ones, a spinner while any is posting), and its popover lists them with their place, a failed one with its error, Retry (which posts everything outgoing) and Discard (`RemoveMessage`, which the backend refuses for a comment that is posting), and posts them with the same `PostingControls`. The form's state (`platform.review`) lives in the platform store, so both places share it and switching tool windows does not empty it. While the platform cannot be synced with, posting is disabled and drafts stay local.

The Comments tool's rail icon counts the unread comments. Those are what others said on the pull request as a whole, the conversation's entries and the messages of the changeset's own threads (`unread.ts`); comments on lines show at their lines and do not count. The time the tool window was last open is kept per pull request in the browser storage (`commentsSeen.svelte.ts`, under the pull request's remote and number, whichever clone shows it); while the tool window is open on the review screen what comes in is seen, and `App` hands the count to `ToolRail`.

## Semantics

Hover, go to definition and diagnostics reach every editor through `editor/semantic.ts`, which asks its owner through `SemanticHooks` (Cmd/Ctrl+B is the `review.goToDefinition` command, reading the focused editor that `semantic.ts` tags); `bindRevision` fixes the revision of a view's requests, since the backend rejects a stale one. `state/semantic.svelte.ts` drops a stale answer.

- Positions are 0-based lines and UTF-16 columns of the side asked about. In a unified view the deleted lines are widgets outside the document, so `editor/deletedLines.ts` maps the pointer to a base position from the DOM.
- Hover text comes from an external process and is untrusted: `lib/hoverMarkdown.ts` renders it with raw HTML escaped, no images and no link targets.
- Diagnostics are drawn only where the editor shows text: a region collapsed behind an "N unchanged lines" bar shows none, nor does the bar, and they appear when the region is expanded (`editor/hiddenRanges.ts` cuts a range by the hidden regions; `editor/semantic.ts` draws what is left).
- Unavailable (SPEC I6) is never shown as nothing: `state/semanticSummary.ts` turns it into the footer's language-server text.

## Where things go

- New screen: `features/<name>/` with an `index.ts`; mount it from `app/App.svelte`.
- New backend request: a method in `state/backend.ts`, then a store field if the UI displays it. A request that can fail in a way the viewer should hear about goes through the store, which sets `session.notice` (shown as a `Toast` in `App`).
- Data the protocol does not carry yet is an optional prop whose absence renders a neutral empty state.
- Colour or size: `lib/theme/tokens.css` (and a `dev` check in both themes).
- New sidebar tool: an entry in `TOOL_WINDOWS` (`state/appCommands.ts`), which gives it its command and menu entry, an icon in `chrome/ToolRail`, and its content: a case in `ReviewScreen` for the left rail, the `side` snippet of `App` for the right.
- New settings page: a component in `features/settings/` and an entry in `SettingsDialog`'s page list.
- New kind of changeset in the queue: the backend's `ChangesetKey` variant, and the tab it is listed under in `queueRows.categoryOf`.
- New tab kind (the Changes, file and log tabs are the kinds so far): an id in `Tabs.svelte.ts`, a pane in `ReviewScreen`, and a case in `ReviewController.build`.
- Anything that differs by platform: a trait the backend sends in `PlatformTraits`, read in the component; never the platform's name (`lib/platformName.ts` only words it).
- A web address to show in the browser: `openUrl` in `state/host.ts`.
- New action with a key or a menu entry: a command registered with `commands`, named by id in the menu descriptions that offer it.
