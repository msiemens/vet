# Architecture

What Vet does is in `SPEC.md`; the UI is built as `ui/ARCHITECTURE.md` says. This file is the backend: the Rust crates under `crates/`, how they depend on each other and where each concept lives.

## Snapshots and the store

A snapshot is a content-addressed tree (`SnapshotId`, a Merkle id over its entries). Where it came from (a commit, the live tree) lives in `Acquisition` and nowhere else (I1): the review model and the semantic layer see snapshots only. `Acquisition` reads blobs through git or, for content git does not hold, from the store.

The SQLite store (`vet-infra/src/store`, migrated at open) keeps:

- `snapshot`, `snapshot_path`, `tree_node`, `tree_child`: retained snapshots and their trees.
- `changeset`: one row per reviewed thing, unique by `(repo, kind, key)`: kind working tree, branch (key is the name) or pull request (key is `host/path#number`), `lens`, the lens the viewer last chose (none until they did), and for a pull request its `title`, `draft` state and `target_branch` (the branch it is merged into) as the platform last said them, for a working tree its `pinned_base` (the commit it is compared against while no review is open), so that a restored review is headed before the platform is asked, and the viewer's pending vote (`vote`, with `vote_posting_since` and `vote_error` encoding its `Outgoing` like a message's).
- `version`: a review's states, numbered from 1; starting a review discards the changeset's earlier versions and numbers its own from 1. Base and target snapshot (empty for a version whose commits the platform dropped), base commit, tip commit, time, origin (`Settled`, `Observed`). Version 0 is virtual: the base the review started from, as a tree without a change, never stored.
- `version_file`: for each version the files it changed against the version before it, with lines added and removed. They are written with the version, and the version list serves them, so the timeline needs no diff per row.
- `review`: how the base was fixed (`MergeBase` of a reference, or a commit), when it opened and closed, `last_reviewed` (the version something was last marked in), whether it finished complete, and the summary of how far it was when last measured (so the queue lists it without diffing).
- `span`, `anchor`, `ack`: the marks of a review; a span's `origin_commit` is the commit whose own diff it was marked in, none for the changeset as a whole. `thread`, `message`: threads, which belong to the changeset and outlive a review. For a pull request's threads, `thread` also holds `on_platform`, `remote_id` (none for a draft), `resolvable`, `resolved_by` and `status_pending` (the viewer's status change not yet sent), and `message` holds `remote_id`, `edited_at`, `synced` (the text the platform had at the last sync), `conflict_body`/`conflict_at` (the platform's text of an edit made in two places) and, for the viewer's comment on its way to the platform, `posting_since` (handed over without an answer yet) and `post_error` (why the platform refused it).
- `project_trust`: the repositories the viewer trusted, and for a pull request the head commit it was trusted at (on its `changeset` row, with whether its head is in a fork).
- `pull_request`: what a platform last said of a pull request besides its threads, one row per `(host, path, number)`: its head and `updatedAt` when read, when Vet read it, and the details, bounded at 256 rows, the least recently read evicted first.
- `project_filter`, `project_filter_item`: the repository's review filter; `backend_setting`, `preference`, `recent_project`, `server_path`: the backend's settings, the window's preferences, the recent list and custom server paths.

Spans are recorded as marked and never remapped in place; remapping starts from them whenever the target changes, and its result lives in memory. `refs/vet/changesets/<changeset>/<n>/…` keep each version's commits alive in git; `vet-app/src/gc.rs` decides what the store keeps alive (SPEC §8). One contract of the store ports (`vet-app/src/store_contract.rs`) runs against the in-memory fake and against `SqliteStore` (through the `contract` feature, so `vet-app` need not depend on `vet-infra`); the settings and gc ports, which have no fake, run against the real store alone.

## The live session

`vet-app/src/session.rs` documents the lifecycle. A project is _browsing_ until the first review action (a mark, an acknowledgement, a thread) starts a _review_ at version 1; a pull request starts with one version per push its platform recorded, the last being the push it is at. From then on each settled snapshot and each observed move of a branch is the next version, and each push the platform lists for a pull request is one too. Finishing returns to browsing and keeps the review's marks in the store.

- **Revision:** a counter that increases with every settled snapshot, observed move, filter change, changeset switch and finished review. Requests about positions carry the revision they were made at and fail as stale otherwise. `Revisions` (a `watch` of the newest revision) lets semantic work for an older revision be dropped.
- **One changeset on view per project** (`Source`): the working tree, a local or remote-tracking branch, or a pull request. `OpenChangeset` parks the state of the one on view and takes up the other's; `ChangesetOpened` tells every subscriber, which fetches the manifest again.
- **Settling** (`settle.rs`): the watcher (`vet-infra/src/watch.rs`) reports `Dirty` paths, `MustRescan` and `RefsMoved`; a quiet period turns them into a settled scan of the worktree. `.git/HEAD` and `.git/index` force a rescan. A change under `.git/refs` or `packed-refs` (a commit on any branch, a fetch) or to `.git/HEAD` (a checkout, a commit on a detached `HEAD`) is `RefsMoved`: the session looks at the changeset on view again (`observe`). For a branch, if its tip or merge base differs from the last seen, the target and base follow and, with a review open, the change is the next version (origin `Observed`); a pull request gains one version per push its platform lists after the recorded ones. For the working tree it only looks whether `HEAD` still builds on the base (below). Settling a tree refreshes the session's `HEAD` and, with a review open and `HEAD` moved, sets the version's `tip` ref. Edits that wait to settle are announced as `EditsPending`. A settled tree is announced only while the working tree is on view.
- **Targets:** the working tree's target is the live tree. A branch's or pull request's target is its tip commit, built from git as a snapshot and never settled; the semantic layer serves it from a materialized snapshot.

### Bases

A base is fixed by the changeset's kind and never chosen (`ChangesetKind`, `LiveSession::base_for`; `BaseChoice` is the internal form, `MergeBase { reference }` or `Commit { id }`, resolved against the changeset's tip). The queue's line counts use the same rule, so a row and its view agree. A pull request's is the merge base with the fetched target branch; a local branch's the merge base with the repository's default branch (its own tip when there is none); the working tree's is the `HEAD` it was opened at. The merge bases follow their branches when `observe` sees them move, never their tips, so the review shows what the changeset adds. The working tree's base is pinned: stored as `changeset.pinned_base` while browsing, so it survives restarts, and cleared when a review finishes, so the next session pins the `HEAD` it finds; a review in progress keeps it in its versions. Commits on top of the pinned `HEAD` (an agent's) do not move it. When `HEAD` no longer builds on the base (a rebase, a reset), `Base::head_off_base` tells the UI, because the changes then include work from elsewhere; `RefsMoved` re-checks it and so does every settle. When the merge base is the tip itself, the target already contains the changeset: the manifest's `Base::contained_in` names it and the changeset is empty. `Base::into` names the branch a pull request is merged into when that is not the default branch (read from the stored `target_branch`). `Manifest.changeset_base` is the base of the changeset as a whole, whatever view the manifest is of.

### Versions and views

`Versions` lists the open review's versions with their `version_file` deltas. Every request that reads or marks the changeset's files carries a `View`: `Changeset` (the changeset as it is) or `Interdiff { from, to }` (`session/interdiff.rs`, on `vet_core::version_diff` and `interdiff`). An interdiff compares version `from`'s target, rebased onto the base of version `to`, with `to`'s target, so what only a base move explains drops out. `from` may be 0, the virtual version of the base the review started from, so the view shows all that `to` changes. Its value is kept by the engine under the four snapshots it compares (base and target of both versions; `session/derived.rs`), not per revision, so a revision that leaves the snapshots equal (a filter, a finished review) finds it. It has no review state of its own, and a mark in it is recorded in the changeset of the newer version (which must be the latest), so seen state carries over. Threads shown in a range are those of its newer version's side.

### Lenses

A branch or pull request is reviewed in a `Lens`: `Squash` (All changes, the default) or `PerCommit` (By commit), kept per changeset in `changeset.lens` (`SetLens`; `ManifestView.lens` and `commits` tell a client). `Commits` lists the changeset's commits oldest first as `CommitUnit`s, each with its own line delta and completion (`session/lens.rs`); the working tree has none. `View::Commit { index }` is a third view beside `Changeset` and `Interdiff`: a commit compared with its parent, with the same manifest, file and mark requests.

- **Merges.** A merge commit is compared with the automatic merge of its parents (`vet-infra/src/git/remerge.rs`, gix's tree merge written to memory only), so it shows what the person who made it decided, as `git show --remerge-diff`. A merge that equals the automatic merge is `clean`: nothing to review and complete. Conflicts the merge could not resolve are kept as marker lines in the files. A merge of more than two parents has no remerge and is compared with its first parent (`CommitKind::Merge { remerged: false }`).
- **Marks.** A span records the commit whose diff it was marked in (`SpanOrigin`, `span.origin_commit`; `Squash` for the changeset as a whole). Marks are content, so remapping carries them between the changeset and its commits wherever the same lines appear (I3); comments are always made in the changeset.

### Base-changed lines

A hunk marked seen against an earlier base is `SeenAgainstOldBase`. `FileReview.old_base_lines` gives, per hunk, how many of its changed lines only such spans cover, and every `Completion` carries the total (`old_base_lines`), which counts as unseen in `seen_lines`. `ReconfirmFile` marks a file's old-base hunks seen again against the current base; toggling one such hunk does the same for it. `BaseDiff` (`session/base_diff.rs`) answers for one such hunk with the base-side lines as they were when it was marked, as a diff to the lines the base has now, and the two base commits; it serves the changeset view only.

A flag for later review is a span too (`SpanState::Flagged`), stored, remapped and cut like seen spans but kept out of the seen coverage: `ToggleFlag` only touches flagged spans and marking seen only seen ones, a hunk counts as flagged while any of its changed lines is covered (`FileReview.flagged`), and it never degrades to the old base. `Completion.flagged_hunks` counts them; finishing a review drops them with the other marks.

### Changeset listing

`ListChangesets` is local: the working tree first, every local branch, then the remote-tracking branches that have commits the default branch lacks and were committed to recently (always the one on view and any with a review open), each group by last commit. A row carries the branch the working tree is on, ahead and behind counts, open threads, and what Vet has of the review (`RowReview`: none, open with version and `last_reviewed`, finished). `ChangesetLines` counts a row's changed lines from the same base rule (`LiveSession::base_for`), a few rows at a time, and pushes each count as it is made (`ChangesetLinesChanged`). `ListPullRequests` asks the platforms (below) and answers separately, so the local list never waits for the network.

### Text search

`Search` (`vet-protocol/src/search.rs`) answers `SearchResults`: the lines of the files in a `SearchScope` that a `SearchPattern` (text, match case, whole word, regex) matches, grouped by file in path order. `SearchScope::View` is the changed files of a `View` in the review filter's sight, each as the diff shows it (`side`, `only_changes` and `not_seen` narrow the lines); `Repository` is every file of the target snapshot, the changed ones with their review state, and the filter does not apply. A `mask` of globs separated by commas, `!` excluding, limits the files (`vet_core::filter::FileMask`, read as the review filter's globs are). A found file carries its hunks with their review states, so a client can draw a preview of a match, and a found line its text (cut to the part round its first match when long) and its matches as UTF-16 columns.

`vet-app/src/search.rs` is the pure part: which lines of a file's two texts are looked at (a context line counts once, a hunk's removed lines come before its added ones, lines split as an editor splits them) and the matches in them; how one line is matched is the port `LineMatcher`, which `vet-infra/src/search.rs` (`RegexMatcher`, on the `regex` crate) implements: a literal is escaped, a whole word is wrapped in `\b`, and a pattern the engine rejects fails the request with a message fit to show. `session/search.rs` (`LiveSession::search`) walks the files; it stops at `MAX_HITS` (1000) matches whatever limit was asked (`truncated`) and yields between files, so a request that was cancelled, or whose connection closed, stops reading and others get their turn. `ListFiles` answers the target snapshot's paths in byte order (no symlink or submodule), for a search by name. `vet-backend/src/contract.rs` classifies `Search`, `ListFiles` and `WorkspaceSymbols` as queries.

## Pull requests and platforms

A pull request is a changeset (`ChangesetKey::PullRequest { remote, number }`). `vet-app/src/pull_request.rs` names its refs: the head is fetched into `refs/vet/pr/<repository>/<n>/head` and the target branch into `.../<n>/target`, apart from every branch and remote-tracking ref of the user's. What is fetched into the head ref depends on the platform: GitHub's `refs/pull/<n>/head` (forks too); for Azure DevOps, which has no such ref, the source branch, or the head commit id when the branch is in a fork's repository. The base is the merge base of the head with the fetched target; each push the platform lists is a version, the newest announced as `SnapshotSettled`. Opening one fetches first, as a task, and fails with a message fit to show. Vet never writes `refs/heads/*`, the index, the worktree or `HEAD`. A pull request a listing no longer has, whose refs were fetched, has them dropped unless it is on view or its review is open (`LiveSession::prunable`).

The title and draft state of a pull request are stored with its changeset when the platform tells of them (opening one fetches them; `LiveSession::remember_pull_request_head`); `Target.title` and `Target.draft` are read from there, so a view of a pull request, also a restored one, is headed without asking again, and are absent for one the platform was never asked about. `Target.head` is a branch's or pull request's tip by its full commit id (absent for the working tree); the UI shortens it to show it. The list always includes the pull request on view, whoever's it is. What a platform last said of a pull request besides its threads is kept in the store and answered from there first (`LiveSession::discussion`), so a revisit is headed before the platform is asked; after a listing, the details of the newest listed pull requests whose `updatedAt` changed are fetched ahead, paced, and stopped while their account is limited or failing (`vet-backend/src/changesets.rs`).

The platform port (`vet-app/src/platform/port.rs`: `traits`, `viewer`, `list_pull_requests`, `pull_request`, `checks`, `check_log`, `forget_checks`, `steps`, `pipeline_action`, and the discussion calls below) is the only platform knowledge outside the adapters. `vet-infra/src/platform/github` (on `octocrab`: GraphQL for lists and discussion, conditional REST for the rest) and `azure_devops` (on `azure_devops_rust_api`; iterations are pushes) implement it. `host.rs` and `remote.rs` decide which platform a host is and which repository a remote URL names (a host that is neither GitHub nor Azure DevOps, and one the viewer has no account for, is refused with a reason); `queue.rs` decides which pull requests belong on the list and what a row shows, purely. `vet-backend/src/hosting.rs` is the `Platform` that forwards to the adapter of the pull request on view; every handler that talks to a platform goes through it, so nothing above the port names a platform.

### Threads, posting and checks

`PlatformTraits` (`platform/model.rs`) describes a platform as data (SPEC §11); the UI branches on the traits it is sent. GitHub: a flat conversation feed, drafts submitted together as one review with a verdict. Azure DevOps: no conversation feed, resolvable whole-PR threads, comments posted one at a time, and a vote set apart from posting.

- **Sync** (`platform/discussion.rs`: the platform's threads, comments and reviewers in common terms; `platform/sync.rs`: `reconcile`, which decides as data what becomes of each thread's status and each comment's text; `session/sync.rs`: applying it). The platform is asked with the session's lock released. A status the viewer changed since the last sync wins and is sent; an edit to a posted comment is sent at once, and if the platform's text also changed since the last sync nothing is sent and both texts are kept (`message.conflict_body`) until `KeepEdit` chooses one; a thread deleted on the platform is removed, with a `SyncNotice` naming the drafts that went with it. Remote positions are mapped onto Vet anchors in the commit the comment was made on. `vet-backend/src/sync.rs` runs it when a pull request opens, on fetch and after a review is posted, and tells subscribers.
- **Posting.** Each outgoing comment has a stored state (`Outgoing`): a draft, posting, or failed with the platform's reason; it is posted once the platform has it. It is written as posting before the platform is asked, so that a post Vet did not see through (the app stopped, the answer was lost) is looked for at the next sync, as a comment of the viewer's with the same text in the same place made since posting began, and settled as posted, or as a draft again. `SubmitReview` posts all drafts as one review with a verdict and an optional text, for a `BatchedReview` platform; if the platform refuses the review, nothing of it is posted and every draft is marked failed. `PostDrafts` posts them one after the other for a `PerComment` platform and stops at the first refusal, which is marked failed, the earlier ones staying posted. A failed comment is posted again with the next post, and `ReviewSubmitted.problem` says why a post stopped short. On a `verdict_separate` platform the vote is outgoing too: `StageVote` stores it as the pull request's `PendingVote` (at most one; the viewer's current vote clears it), `DiscardVote` drops it, and `PostDrafts` sends it after the comments unless they stopped short; a vote left posting is settled by the next sync against the platform's `viewer_verdict`. A request for the wrong kind of platform fails. Drafts whose code is gone and those in a thread with an edit conflict wait. A comment on the whole pull request that the platform refuses reaches the viewer as a `Notification` with its text.
- **Status.** `PlatformStatus` says how the platform of the pull request on view is doing (`Ok`, `SignedOut`, `TokenExpired`, `Failed`), sent to every subscriber after each sync; `PullRequestInfo` answers with what the Comments panel shows above the threads (state, author, branches, reviewers and the viewer's vote, checks, what blocks the merge) as the last sync found it. `Notification` is a tagged enum of what happened — a thread deleted on the platform, a vote or comments not posted, a server died, a sync stopped — which the UI words; they are cards for the window's corner and the footer's bell list, and the backend keeps no list.
- **Checks.** The backend keeps the checks of the commits on view fresh itself while the queue or the review screen shows the pull request, and pushes each round as `ChecksChanged` (`vet-backend/src/checks.rs`); `Checks` asks once. A platform keeps what it learnt of a commit whose checks are all done and asks again for one that runs. A commit it cannot answer for is left out with the reason beside the others. `CheckLog` gives the log of a run, without timestamps or colour codes, and where it failed; GitHub's is an Actions job log, Azure DevOps's the log of the failed step of the build a policy evaluation names. Azure DevOps checks are the statuses services post to an iteration and the pull request's policy evaluations, which count for the head commit only. No check or log is stored.

Credentials (`platform/accounts.rs`, per account and not per session: a host for GitHub, an organization, `dev.azure.com/{org}`, for Azure DevOps, as `RemoteKey::account()` names it) are held in memory only, tried in order: the token of a signed-in `gh` or `az` (`cli.rs`), then the token the shell hands over from its keychain (`SetCredentials`; the backend asks with the `CredentialsNeeded` event), validated against the platform when entered by the viewer. `vet-infra/src/credentials.rs` asks the platform whom a token belongs to. A token goes to its host's API and nowhere else. No request or response is logged; a failure is, at `warn` through `tracing`, with the account, endpoint, status and the platform's reason and never a token.

`fetch.rs` keeps remote-tracking refs current: every remote, as one background task, on demand (`Fetch`) and every five minutes while a project is open; afterwards `ChangesetsChanged` tells the subscribers.

## The semantic layer

`vet-semantic` is pure; `vet-infra` implements its ports over language-server processes. Servers are pooled by `(target, backend, policy)`, kept warm and evicted least recently used; a start is an engine flight keyed by the pool key and a generation (a settings change or an install begins a new one), and each server has a request budget (`vet_semantic::gate::Gate`) so that many analyses cannot pile requests on it. `RestartServer` replaces a language's servers at once (`Pool::restart_now`; requests underway fail as restarted). The pool supervises what it started (`LanguageServer::exited`, watched through the `Detach` port): a server that dies is started again once, and one that dies again within `RESTART_WINDOW` stays `Stopped` until a manual restart; the backend tells the viewer with a `Notification` and `ServersChanged`. The live tree is served in place; every other snapshot is served from a directory the `Materializer` produced. A policy that forbids executing project code refuses the backends that would.

**Languages and features.** `vet-infra/src/language.rs` lists the languages (Rust, TypeScript, Python, C#, Svelte, Angular, YAML, JSON, Bash, Dockerfile), each with its server, install, restore and the files it serves. A server serves a file by extension or by `ServerConfig::file_names` (`Dockerfile`, and `Dockerfile.dev`), and, when `ServerConfig::requires` names files (Angular's HTML needs an `angular.json` in the file's directory or above), only where one is found; `Semantic::finding` gives it the lookup (`Finds`), which `vet-backend/src/open.rs` wires to `vet_infra::is_file_in` on the checkout, a snapshot's layout being taken to be the checkout's. A server is unsupported only if it cannot take documents. What else it offers is read from `initialize` (`lsp/capabilities.rs`) into `vet_semantic::ports::Features` (one `Feature` per operation: document symbols, definition, references, implementations, hover, call hierarchy, workspace symbols), kept by the pool (`Pool::features`, `ServerInfo.features`, none until a server has started). A query for an operation the server lacks is answered before the server is asked, with `SemanticError::NotOffered` (`UnavailableKind::NotOffered`), never with an empty answer (I6).

**Server setup.** What a server is told besides the protocol is decided in `vet-infra/src/lsp/setup.rs`: arguments, `initialize` options, settings (answered to its `workspace/configuration` requests by section and sent with `workspace/didChangeConfiguration`), notifications after `initialized`, and whether to wait for it to ask for its settings. `lsp/rpc.rs` (`Replies`) answers the server's requests with them. The YAML and JSON servers check files against JSON schemas: `vet-infra/src/schemas.rs` bundles a fixed set and, unless the analysis policy allows executing restores (`AnalysisPolicy::allow_schema_downloads`), answers every `vscode/content` request for a schema itself or refuses it, and `custom/schema/request` by the file's name, so a repository cannot make the machine fetch an address it chose. The identity of a server covers all of this: its setup, the packages installed beside it, and either the bundle's fingerprint or, when schemas come from the network, a name for this run of Vet, so that answers given online are reused only within it. The JavaScript languages (TypeScript, Svelte, Angular) share one restore record of a tree, and languages that need none (YAML, JSON, Bash, Dockerfile) plan no restore.

**Reuse (I2).** An answer is reused only under a key that names everything it depends on (`reuse.rs`). `Key::Text` is for answers that depend on one text, the symbols a document declares: the server's identity, the file extension and the text's blob id, valid on any tree and either side. `Key::Project` is for answers that resolve across files: the server's identity, a `Basis` (snapshot, analysis policy, restore fingerprint, or the numbered server instance when nothing was recorded of the restore) and the query. The live tree has no project key, so its answers are asked fresh. The server's identity (`ServerLauncher::identify`, under the analysis policy) covers binary, version, settings and toolchain, so a changed server misses on every key and nothing needs deleting. `Answers` is a bounded in-memory LRU over the engine, with a flight per key: a question is asked of the server once however many callers ask it, and however many of them give up. An answer is admitted only if the server was idle when asked and its readiness epoch did not change before it answered, and an error is never kept. The answers that persist (`Key::persists`: the symbols of a text, and the answers about a tree whose restore was recorded, but not workspace queries) are also stored in a SQLite file of their own, `semantic-cache.sqlite` (`vet-infra/src/semantic_cache.rs`, opened by `vet-backend/src/caches.rs`), and read from it before a server is asked; the file is disposable, holds a size budget the viewer sets, and loses least recently used rows first. Every answer carries its provenance (the server, and whether it came from the cache).

**Changed symbols** are derived from keyed primitives alone, one changed file at a time. `FileSymbols` (`Semantics::file_symbols` in `vet-app/src/semantics.rs`) takes the base and target text of one changed file through the `Texts` port (implemented over the acquisition's blobs), asks `text_symbols` for each side and intersects them with the hunks (`derived/changed.rs`): the file's changed symbols, and the unchanged symbols that hold them, which the Changes tree shows as context. The backend analyses the changeset's files itself while the review screen shows it, the files with an open tab first (`vet_app::analysis::open_first`), a few at once, and pushes each file's answer with the progress (`vet-backend/src/symbols.rs`). Since the symbols of a text are kept (I2), asking again for a file whose texts did not change asks no server. `FileOutline` lists every symbol of one file for the Structure tool, the changed ones marked; in a commit view the backend reads that commit's text and outlines it without marks (`text_outline`), since the semantic layer holds only the changeset's snapshots. `SymbolAt` (`derived/cursor.rs`) names the symbol that holds a position on either side, changed or not, for the panel that follows the editor's cursor. The changed files' diagnostics are analysed the same way, target side first and then the comparison with the base, and pushed as `FileDiagnostics` with the origins (`vet-backend/src/problems.rs`). For any symbol, changed or not, `Calls` (`derived/calls.rs`: changed callers followed through changed symbols, changed callees, and for a changed symbol its unchanged direct callers as possibly affected, with a gap where the walk was cut), `Usages`, `Signature`, `Reachability` and `RemovalImpact` derive their answer from project-keyed primitives.

**Symbols by name.** `WorkspaceSymbols` (`Semantics::workspace_symbols`) is Search Everywhere's symbol search: `workspace/symbol` on the target side, asked of the server of every language that has a file in the target (found once per revision, since it walks the snapshot), all together so that a cold server does not hold the others back. Each language answers as a `LanguageSymbols`: its symbols in the server's own order, or `failure`, an `Unavailable` saying why it could not (not installed, not trusted to run, not offered); the others still answer.

**Revisions.** `Semantics` runs a request's work through `Revisions::until_superseded`; once a newer revision is known the work is dropped, with the server requests it waits on (a dropped request is cancelled with `$/cancelRequest`), and the request fails as stale.

**Kept trees.** Materialized trees live under Vet's data directory, one per `(snapshot, policy)`, built in staging and renamed so a directory under a key is complete (`vet-infra/src/materialize/kept.rs`). Locks outside the tree are shared by users and exclusive for the gc, which removes trees beyond a disk budget or idle for too long. Each language's restore is recorded beside the tree with a fingerprint, so a later launch starts its servers without copying or restoring again.

## Concurrency

Three lanes own their resources and share nothing but the engine: the review lane (the commands that change review state), the semantic lane (`Semantics` and the pool) and the platform lane (exchanges with a platform, serialized by the session's `exchange` lock, with the state released while the platform is asked).

- **Commands.** A review command (a mark, a thread, settling, an observed move, a filter or lens change, opening a changeset, starting or finishing a review) takes the write token (`LiveSession::hold`, FIFO) and gets a `Held` (`vet-app/src/session/hold.rs`): the token and a copy-on-write `Arc<State>`. Reading dereferences it; the first change copies the state, which is cheap because the snapshots, spans and anchored texts are behind `Arc`s. `Held::publish`, or dropping the `Held`, makes the copy the state readers see. A command that announces a new revision publishes first, so whoever hears of it finds it. Holding the token a command awaits its own store connection, git ref writes on the review's I/O budget and engine flights of the review kinds, and never a language server, a platform or the semantic budgets; settling works its content and the diff it installs out before it takes the token, and a command publishes only a state it has finished putting together, with the review state remapped onto the new revision. Every change through a `Held` takes the project's next change sequence (`State.seq`); `ReviewUpdate.seq` and `Manifest.seq` carry it, so the UI applies an answer or an event only if it is newer than what it holds, and a manifest never overwrites a newer mark.
- **Writes are typed.** `ReviewWrites` (`vet-app/src/ports.rs`) holds every change to the review database; the read traits (`Store`, `ChangesetStore`, `ReviewStore`, `ThreadStore`) have none. `LiveStore::writes()` gives the store's write connection (`vet_infra::store::ReviewWriter`) to the session, which keeps it inside the token and hands it out as `Held::writes()`, so only a command that holds the token can write. A read pool of connections serves everything else.
- **Readers.** A request reads the published pointer (`Published`, a `std::sync::Mutex<Arc<State>>` locked only to clone or swap) and never waits for a command, however long it runs; it sees the state as one command left it, never between two of its steps. What the state lacks to answer (the diff of its sides, an interdiff, the commits of the changeset) it gets from the engine without any lock, and it takes the token only to install that when the state has none (a cold start, an evicted value).
- **The semantic lane reads a `RevisionView`** (`session/revision.rs`): a clone of the acquisition and of the published pointer, giving a revision's sides, a file per key and its changed files. It cannot take the token and has no handle to the review database, so semantic work cannot make a command wait and no command waits for it.
- **Derived work** is computed once per key by `vet-engine`. The review's kinds (`session/derived.rs`: the diff of two snapshots with its texts, an interdiff, the commits of a changeset with the diff of each) are `Kept`, keyed by the ids of the snapshots or commits they are made from and bounded by count and by the bytes of text they hold; the semantic layer's answers, server starts and identities are engine kinds too. A flight is driven by whichever waiter is polled, so the caller that started it going away starts nothing over; one with no waiter left is dropped, with the server requests it waits on cancelled. `Tasks` for derived work come from the engine (`Engine::observing`), one per flight however many callers.
- **Budgets.** Every way the backend leaves the async threads draws on a bound (`vet-infra/src/budget.rs`): `review_io` and `semantic_io` for the blocking work of the two lanes, `background_io` for work nobody waits for (the copy of the working tree's content ahead of a review, which starts once the tree has been quiet for a moment), `probes` and `restores` for the processes that answer a question and the steps of a restore. A lane cannot take another's permits, so a semantic lane that saturates its own leaves the review's reads alone. Adapters get their lane's budget when `vet-backend/src/open.rs` wires them. A fetch holds a budget of its own, since it takes as long as the network does.
- **Lints keep it so.** `crates/clippy.toml` bans `tokio::task::spawn_blocking`, `tokio::runtime::Handle::spawn_blocking`, `std::thread::spawn`, `std::process::Command::new` and `tokio::process::Command::new`: blocking work goes through `Budget::blocking` and processes through `exec`, the two modules that allow them with `#[allow(clippy::disallowed_methods)]`. The other exceptions are the transport's stdin thread, a Windows junction call in `restore/reuse.rs` and the tests that build fixtures with git. The file covers the workspace crates and not `ui/src-tauri`, and `ci/quick.sh` treats a change of it as a change of every crate. `vet-backend/tests/it/load.rs` is the test of the whole: with every semantic request stuck, review requests still answer.

## Events and background work

The backend pushes `SnapshotSettled`, `ChangesetOpened`, `ReviewChanged`, `ReviewStarted`, `LensChanged`, `TargetChanged`, `ChangesetsChanged`, `ChangesetLinesChanged`, `ThreadsChanged`, `EditsPending`, `FileSymbols`, `FileDiagnostics`, `ChecksChanged`, `RestoreFailed`, `ServersChanged`, `ServerRuntimes`, `ServerInstallOutput`, `PlatformStatus`, `Task` and `Notification` to the subscribers of a project, and `CredentialsNeeded`, `AccountsChanged`, `RecentProjectsChanged`, `SettingsChanged` and `PreferenceChanged` to the connections that asked to `Subscribe`. Every event a request causes goes to every subscriber, the requester included: of the requester's stores only the one that asked reads the answer, and the others learn of the change from the event. A connection that joins a project while edits wait to settle is told `EditsPending` at once. A mutation announces its own events and leaves them to no later sync. `vet-backend/src/contract.rs` classifies every request as a query, as unannounced (with the reason) or as a mutation with the events it sends, exhaustively, so a new request cannot be added unclassified; its test drives every mutation it can with two connections and checks that both hear what is declared. A client refetches what a revision change invalidates. Long work (scan, diff, restore, server start and indexing, fetch, comparing versions) reports as `Task`s through `vet-app/src/progress.rs`, throttled, and `Tasks` answers a connection that joined late with the running ones. `WaitForQuiet` answers once the project has no background work at all: no task, no counted background work (counted in every build), no edit waiting to settle, no settled result the session has yet to announce and no reconcile the settle loop has not made. Its answer is ordered after the earlier events on the connection.

## Logging

`vet-log` installs the one subscriber, in the backend and in the Tauri shell: a daily rolling file in the `logs` folder of the data directory (`vet.log.<date>`, five days kept) through a non-blocking writer, plus stderr in debug builds; `VET_LOG` sets the level in `RUST_LOG` syntax, `info` by default. The transport opens a span per request (`request{id, kind, project}`, the project recorded once the handler resolves it) around its handler, so every line logged while it runs carries that context. Timing is `debug` under the target `timing` (`VET_LOG=timing=debug,info`). The UI sends uncaught errors, unhandled rejections and failed requests as `ClientMessage::Log`, logged under the target `ui`; `LogDirectory` tells it where the files are for Help > Show Log. Nothing at `info` or above carries a token, a credential or file content; a tool's output is cut to its first line there.

## Where things go

- A rule about what a review is: `vet-core`, with tests on plain values.
- A use case: a module of `vet-app` over ports it declares; the adapter for a new port goes in `vet-infra`.
- A new request or event: `vet-protocol`, then `vet-mapping` for its views and `vet-backend` for the handler, its classification in `vet-backend/src/contract.rs` (what it changes, which events tell every subscriber), and the typed call in `ui/src/state/backend.ts`.
- A change to review state: a command of `vet-app`'s session that takes the write token and publishes; a derived value (a diff, an analysis): a kind of `vet-engine`, awaited without the token. Blocking work and processes go through `vet_infra::budget` and `exec`.
- A semantic query: a primitive on `LanguageServer`, a key for it in `reuse.rs`, a `Feature` if servers may lack it, a derived analysis in `vet-semantic/src/derived`.
- A new language server: a `Language` in `vet-infra/src/language.rs` (what it serves, its install and restore, its setup in `lsp/setup.rs`).
- A new hosting platform: an adapter of the port in `vet-infra/src/platform`, its host and remote parsing in `vet-app/src/platform`.
